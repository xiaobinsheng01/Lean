# LEAN 业务说明

本文从业务角度说明这套引擎能完成什么、一次策略从研究到实盘怎么走、以及它不负责什么。技术分层见 [架构方案](架构方案.md)。

## 1. 业务定位

LEAN 服务的是量化研究员和交易开发者。他们要在统一环境里完成四件事：用历史数据验证想法、搜索参数、把同一套代码接到模拟或真实账户、再把结果讲清楚。

产品承诺可以收成一句话：**策略代码不因回测或实盘而重写。** 变化的是数据来源和订单去向，不是 `Initialize` / `OnData` 的写法。

它不是行情终端，不是投资顾问，也不是券商。它不产生交易建议，不托管客户资产。下单后果由所连接的券商账户承担。

## 2. 谁在用，用它做什么

| 角色 | 目标 | 主要入口 |
| --- | --- | --- |
| 策略研究员 | 看历史行情、试指标和股票池，先不关心成交回路 | Research 笔记本、`QuantBook` |
| 量化开发 | 把想法写成可重复运行的算法，比较收益和风险 | `Launcher` 回测 |
| 参数研究者 | 在约束下搜索一组参数，而不是手工改一次跑一次 | Optimizer |
| 交易员 / 部署者 | 用同一代码跑模拟盘或指定券商实盘 | `live-paper` 或 `live-*` 环境 |
| 复核人 | 阅读收益、回撤、换手、持仓和危机区间表现 | Report |
| 数据准备者 | 把外部行情转成引擎能读的文件 | ToolBox、Downloader |

一个人经常先后扮演这几个角色。引擎用不同进程把这些工作分开，避免研究脚本误提交真实订单。

## 3. 业务能力

```mermaid
flowchart LR
    Research[研究] --> Backtest[回测]
    Backtest --> Optimize[参数优化]
    Optimize --> Paper[模拟盘]
    Paper --> Live[实盘]
    Backtest --> Report[绩效报告]
    Live --> Report
    DataPrep[数据准备] --> Research
    DataPrep --> Backtest
```

| 能力 | 业务结果 | 是否会发出真实订单 |
| --- | --- | --- |
| 研究 | 图表、历史序列、临时计算 | 否 |
| 回测 | 一段历史区间上的权益、订单和统计 | 否，成交由模型产生 |
| 优化 | 多组参数的目标值排序 | 否 |
| 模拟盘 | 用实时行情驱动策略，订单在内部撮合 | 否 |
| 实盘 | 订单进入券商账户 | 是 |
| 报告 | 给人和评审看的绩效说明 | 否 |
| 数据下载与转换 | 本地可回放的行情文件 | 否 |

## 4. 策略从想法到上线

### 4.1 研究

研究员在笔记本里用 `QuantBook` 取历史、画图、试过滤条件。这个环境加载的是同一套证券和数据对象，但没有回测主循环，也不会把订单送到券商。研究结论要变成策略，仍需写成 `QCAlgorithm`。

### 4.2 回测

回测回答的是：如果在指定区间、指定行情分辨率和指定成交假设下，这段代码会留下什么持仓和盈亏。

一次回测的业务步骤：

1. 选定算法、语言、起止时间、初始资金和基准。
2. 在 `Initialize` 里声明要交易的资产、周期和股票池。
3. 引擎按时间回放行情。每个时点策略可以读价格、查历史、下单或调仓。
4. 订单按该券商模型的费率、滑点和成交规则变成成交。
5. 公司行为自动调整持仓和现金：分红入账、拆股改数量和价格、退市退出、代码变更跟随。
6. 预热结束后才开始统计。预热只为了让指标和历史窗口就绪。
7. 区间结束或组合净值归零时停止，并给出组合统计和交易统计。

回测结果是假设下的结果。限价能否成交、滑点多大，取决于当时选择的成交模型和行情粒度。Tick 和日线对同一策略可能给出不同结论。

### 4.3 参数优化

优化回答的是：在给定范围内，哪组参数使目标更好，同时满足约束。目标可以是最大化或最小化某个绩效指标，约束用来丢掉不可接受的组合，例如回撤过大。

业务上有两种搜法：

- 网格搜索：把每个参数的取值列全，适合空间小、需要完整对比。
- 欧拉搜索：沿改进方向逐步移动，适合空间大、不要求穷举。

每一组参数都是一次独立回测。优化器限制同时运行的回测数量。失败的回测计入失败数，不当成更优结果。输出是参数与指标的对照，不是一笔可直接下的订单。

### 4.4 模拟盘

模拟盘用实时数据跑策略，订单仍在引擎内部成交。它用来看策略在真实时间里会不会报错、股票池会不会过大、计划任务是否按交易时段触发。它不验证券商拒单、部分成交和断线。

### 4.5 实盘

实盘把订单交给配置中的券商，并用券商回报更新持仓。启动时要用券商账户里的现金和持仓初始化，而不是只用回测里的虚拟资金。

实盘相对回测，业务上多出这些事：

- 账户里已有、但策略不认识的持仓，默认忽略，避免一次部署被无关资产拦住。
- 券商断线和重连会通知策略。策略可以选择等待、对账或停止。
- 历史预热只向券商要最近一段。更早的数据要事先放在本地。
- 人工或系统把状态打成清算时，引擎会尝试平掉持仓。
- 只提供交易、不提供行情的券商，行情要另接 Lean 的数据通道。

同一算法切到实盘，改的是运行环境，不是策略文件。环境决定券商、行情队列和历史来源。

### 4.6 绩效报告

报告把一次结果翻译成可读的说明，而不是再算一遍交易。内容包括累计收益、年度和月度收益、回撤及修复、夏普、索提诺、信息比率、换手、杠杆、资产配置、市场分布、估计容量，以及若干历史危机区间上的表现。它适合复盘和交接，不能替代回测明细里的逐笔订单。

## 5. 策略怎么表达业务意图

有两种写法，可以同时用。

**事件写法。** 策略在 `Initialize` 里声明订阅，在 `OnData` 里看到这一时刻的行情后直接下单。适合规则集中、标的固定的策略。

**框架写法。** 把决策拆成五段，每段只回答一个业务问题：

| 阶段 | 业务问题 | 产出 |
| --- | --- | --- |
| 宇宙选择 | 今天看哪些标的 | 符号集合 |
| Alpha | 看多、看空还是平，信心和有效期是多少 | 观点 Insight |
| 组合构建 | 观点对应多大仓位 | 目标权重或数量 |
| 风险管理 | 哪些目标必须缩小或清掉 | 覆盖后的目标 |
| 执行 | 用什么方式把仓位做到目标 | 订单 |

观点有方向、幅度、信心和到期时间。到期后不再驱动目标仓位。风控可以否决组合构建的结果，例如单标的回撤超过阈值就把它的目标改为零。

这套拆分的业务价值是：换一个选股范围，不必重写下单；换一种执行方式，不必重写信号。

## 6. 交易业务规则

### 6.1 能交易什么

| 资产 | 业务含义 | 需要额外处理的事 |
| --- | --- | --- |
| 股票 | 普通买卖 | 拆股、分红、退市、代码变更、T+n 结算、卖空利率 |
| 股票期权 | 权利金买卖，可行权 | 合约乘数、保证金、行权或到期、组合保证金 |
| 期货 | 保证金交易的远期合约 | 到期换月、保证金、结算 |
| 期货期权 | 标的是期货的期权 | 乘数与标的期货可能不同，一组对应一份期货 |
| 指数 | 通常只作为信号或基准 | 多数不可直接持有 |
| 指数期权 | 现金结算的指数权利 | 行权风格多为欧式 |
| 外汇 | 货币对 | 两种货币的现金余额 |
| CFD | 以保证金跟踪标的的差价合约 | 融资费用、券商可交易时间 |
| 加密现货 | 币币或法币对 | 手续费常从成交资产扣除 |
| 加密合约 | 永续或交割合约 | 资金费率、维持保证金 |

账户是现金账户或保证金账户。现金账户不能靠融资扩大仓位。保证金账户按品种使用不同的购买力规则，而不是一个全局杠杆数字。

### 6.2 订单在业务上代表什么

| 订单 | 业务含义 |
| --- | --- |
| 市价 | 尽快成交，价格由当时行情和滑点决定 |
| 限价 | 只在不差于指定价时成交 |
| 止损市价 | 价格触及触发价后，变成市价 |
| 止损限价 | 触及触发价后，变成限价 |
| 触及限价 | 先到触发价，再挂出限价 |
| 跟踪止损 | 触发价随有利方向移动 |
| 开盘市价 / 收盘市价 | 只在开盘或收盘撮合 |
| 期权行权 | 把权利变成标的持仓或现金 |
| 组合单 | 多腿一起提交，便于按组合计算保证金 |

开仓和平仓在业务上不同。买入可能是开多，也可能是平空。保证金和部分券商按这个意图检查，而不是只看买卖方向。

`SetHoldings` 表达的是目标仓位比例。引擎算出与当前持仓的差额再下单。框架执行模型最终也落到同样的订单上。

### 6.3 成交假设

回测和模拟盘里，成交不是交易所确认，而是规则：

- 这笔订单在当前 bar 或 tick 上能不能成交。
- 成交价要不要再加滑点。
- 手续费收多少，从哪种货币扣。
- 成交后的现金何时能再使用。

实盘里，能否成交、成交价和费用以券商回报为准。策略里设置的费率模型主要用于回测对齐，不能覆盖券商实际扣费。

部分成交会多次通知策略。策略如果按“一次订单等于一次完整成交”来记账，会和持仓不一致。

### 6.4 组合单与保证金优惠

多腿策略可以按头寸组处理。典型例子是备兑看涨：持有标的，同时卖出看涨期权。分开计算时，空头期权要付足额保证金；作为一组时，因为标的覆盖了义务，保证金下降。

业务前提是各腿数量符合同一比例。例如一份标准备兑是 100 股对 1 张合约。数量对不齐的部分不能享受这一组的保证金。

## 7. 数据和股票池在业务上的意义

策略能看见的世界，等于它订阅的数据。没有订阅，就不会在那个时点被唤醒。

分辨率决定决策频率，也决定回测成本：

| 分辨率 | 适合的决策 |
| --- | --- |
| Tick | 逐笔或报价驱动，数据量和偏差都最大 |
| 秒、分钟 | 日内执行和短周期信号 |
| 小时 | 日内但不过度敏感的规则 |
| 日 | 隔夜持仓、基本面和组合再平衡 |

股票池把“交易什么”从写死的代码，变成随时间变化的名单。名单可以来自成交额、基本面、ETF 成分、期货未平仓量或自定义规则。名单变化时，新标的开始接收行情，被移出且已无持仓的标的停止交易。仍有持仓的标的会留到平仓之后。

自定义数据用来引入价格以外的序列，例如另类数据或宏观数据。它能驱动信号，本身不一定可交易。

本地数据是回测的业务原料。文件缺失时，该标的在对应时段没有行情。这会被看成没有交易机会，而不是自动从别处补上。实盘若券商不供数，同样依赖事先准备好的数据通道。

## 8. 绩效怎么读

组合统计回答“账户曲线好不好”：

- 总收益和年化，看赚了多少。
- 最大回撤和修复天数，看跌下去以后多久回到前高。
- 夏普、索提诺，看单位风险换来多少超额。
- 概率夏普，看这个夏普有多可能高于基准。

交易统计回答“单笔质量如何”：胜率、平均盈亏、盈利因子、单笔最大不利偏移、持仓时间。组合很好但交易统计很差，通常说明少数交易主导了结果，样本未必站得住。

报告里的容量是估计值，用来提示策略在更大资金下会不会被自身成交冲击。它不是券商给的额度。

这些数字都依赖成交假设。换滑点、换费率或换分辨率后，排序可能改变。优化如果只盯一个收益数字，容易选出只在这段历史上好看的参数。

## 9. 运行环境对应的业务场景

`Launcher/config.json` 里每个 environment 是一个可部署场景。

| 环境 | 业务场景 |
| --- | --- |
| `backtesting` | 本地历史回放 |
| `live-paper` | 实时行情、内部撮合 |
| `live-interactive` 及各类 `live-*` | 该券商的真实或模拟账户，以券商自身的 paper/live 开关为准 |
| 数据与交易分离的环境 | 券商只收单，行情用另一条通道 |

券商侧还有自己的模拟开关，例如 Interactive Brokers 的 `paper`、Alpaca 的 paper trading、eToro 的 demo。Lean 的 `live-mode` 只表示走实盘处理器，不表示账户一定是真实资金。上线前要同时看两处。

密钥、账户号和数据令牌放在配置里。空令牌意味着对应的数据或券商不可用，而不是自动降级到免费数据。

## 10. 业务边界

引擎负责：

- 按时间把行情交给策略。
- 检查购买力、生成订单、回测中按模型成交。
- 实盘中转发订单并接收券商状态。
- 维护现金、持仓、公司行为和绩效统计。
- 用同一代码跑研究之后的回测、优化和部署。

引擎不负责：

- 保证回测利润能在实盘复现。
- 代替券商做风控、合规和适当性审查。
- 提供全部券商的协议实现。部分券商只有规则模型，连接在独立组件里。
- 自动补齐缺失的历史文件。
- 投资决策。Alpha 和组合模型只是可替换的计算步骤。
- 多用户托管和账户权限。那是 QuantConnect 云或外部系统的事。本地队列一次处理一个作业。

## 11. 上线前要核对的业务清单

1. 回测使用的券商模型，与实盘要去的券商一致，包括订单类型、费率、最小变动价位和是否允许卖空。
2. 分辨率和填充规则与策略假设一致。日线策略不要用日内成交模型解释结果。
3. 股票池规模低于配置里的符号上限，否则订阅会在运行时被拒绝。
4. 预热窗口所需的历史，本地或券商至少有一边能提供。
5. 保证金策略用组合单和头寸组时，各腿比例在回测和实盘都满足。
6. 模拟盘先跑通实时数据、计划任务和断线回调，再切到真实账户。
7. 实盘环境的账户开关是预期的模拟或真实账户。
8. 报告与订单明细一起看。只看夏普或总收益不够判断能否部署。
